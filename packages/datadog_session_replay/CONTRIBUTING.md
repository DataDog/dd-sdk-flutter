It contains all the basic guidance on how to get started will all of the packages including `melos` commands and code style information.

## Working with FFI Code

The Session Replay plugin uses FFI over Method Channels in order to better utilize multiple isolates and multiple threads, instead of having to pass through the Flutter main thread for each message.  We generate our FFI bridges using `ffigen` and `jnigen` when the platform interfaces change.

`ffigen` and `jnigen` configurations are held in separate files from the `pubspec.yaml`.

### Toolchain requirement for running `build_runner`

This package depends on `objective_c`, which ships a native build hook (`hook/build.dart`). Starting with Dart 3.10, `dart compile` refuses to AOT-compile any script whose package graph contains a build hook, and `build_runner` compiles its build script with `dart compile aot-snapshot`. As a result, running `dart run build_runner build` in this package (for example, to regenerate `lib/src/sr_data_models.g.dart` after changing a `json_serializable` model) fails with a generic `Failed to compile build script` error on Dart 3.10.x.

This restriction was relaxed in **Dart 3.11.0 / Flutter 3.41.0**. If you need to run `build_runner` in this package, make sure you're on Flutter 3.41.0 or later.

This only affects local codegen — it does not change the package's supported minimum (Flutter 3.38.0 / Dart 3.10.0 in `pubspec.yaml`). Code generated by `build_runner` should still be Dart 3.10 compliant.

### Regenerating iOS FFI Interfaces

The bridge between Dart and iOS is held in `ios/datadog_session_replay/Sources/FlutterSessionReplayBridge.swift`

To make a change to the iOS FFI interface, you first have to generate a "bridging header" from the Swift code. You can do this by building the Swift package held at [`ios/datadog_session_replay`](./ios/datadog_session_replay/).

```bash
swift build
```

This build will fail, but that's okay. It will still output the necessary bridging header at `ios/datadog_session_replay/Sources/datadog_session_replay_bridge.swift`.

The next step is to regenerate the FFI bindings from the bridging header using the `dart ffigen` command at the root of the pacakage

```bash
dart run ffigen --config ffigen_ios.yaml
```

### Regenerating Andoird FFI Interface

The bridge between Dart and Android is held in `android/src/main/kotlin/com/datadoghq/flutter/sessionreplay/FlutterSessionReplayBridge.kt`.

If you make a change to this interface, you must regenerate the Dart bridge from JNI:

```bash
# From the root
melos run generate:jni_bindings
```

This regenerates the jnigen bindings for every package that declares a `jnigen.yaml` (this package and `datadog_flutter_plugin_android`) and reports a diff; `melos run verify:jni_bindings` runs the same process in check mode without leaving the change in place. jnigen resolves its own Android classpath, so no separate APK build is required first.

## Golden Tests

Flutter Session Replay uses "golden testing" to try to ensure that the SR wireframes remain consistent and are a reasonable representation of the widgets we capture. Each golden test captures a widget tree as SR wireframes, then renders the resulting wireframes using a Flutter `CustomPainter` called `WireframeCustomPainter`. The resulting render is captured and compared to a known good, "golden" image held in `example/golden_test/goldens`. This also allows us to look at the results of simple widget captures without needing to send them to Datadog intake for verification.

To write a new Golden test, follow the examples in `example/golden_test/simple_widget_golden_test.dart`.

If you are making changes and need to test that you have not broken anything in the golden tests, you can run:

```bash
# from ./example
flutter test golden_test
```

If you have made changes that require updating the golden images, run:

```bash
# from ./example
flutter test golden_test --update-goldens
```

## Session Replay data models

`lib/src/generated/sr_data_models.dart` is generated by
[`tools/sr_models_generator`](../../tools/sr_models_generator) from the
[rum-events-format](https://github.com/DataDog/rum-events-format) schemas, at
the commit pinned in `tools/sr_models_generator/sr_models_generator.yaml`, and
its JSON code, `sr_data_models.g.dart`, by `json_serializable`. The
generator also writes the official samples of rum-events-format, which the
tests of the models decode, to `test/generated/sr_samples.dart`. Do not edit
these files by hand: change the schemas or the generator's configuration, and
regenerate them.

```bash
# From the root
melos run generate:sr_models         # generate the models and their JSON code
melos run generate:sr_models:check   # fail if they are not up to date, as CI does
```

### Moving the rum-events-format pin

1. Run `melos run generate:sr_models:update` to pin the latest rum-events-format
   `master`, or `dart run sr_models_generator --ref <branch, tag or SHA>` from
   `tools/sr_models_generator` for another ref, then `dart run build_runner
   build --delete-conflicting-outputs` in this package. The commit is pinned
   only once the models of its schemas are generated. A rename in
   `type_renames` that matches no type fails here: update it.
2. Review the diff of the generated models and samples: new types and fields,
   and changed names.
3. Run `flutter test test/generated` in this package. It decodes the samples
   and the smallest JSON of each union variant. When the schemas change,
   update the variants and the keys the samples drop.
4. Commit the configuration, the generated models and the samples together.
